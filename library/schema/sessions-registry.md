# Sessions registry

Shapes `system/sessions/registry.md` (runtime state, gitignored). Owned by `af session`; never edit it by hand.

```
| name | role | session_id | model | started | last_seen | status | handoff |
|---|---|---|---|---|---|---|---|
| af-main | main | <uuid> | opus | 2026-10-25T09:12 | 2026-10-25T17:40 | live | system/sessions/af-main/handoff.md |
```

- One row per name. Re-registering a name replaces its row and keeps its folder.
- `name`: the chat's name as other chats address it with `SendMessage`: the VS Code session title (set with `/rename`), or `claude --name` from a terminal. One of `af-main`, `life/<topic>`, `project/<slug>`, `system/<topic>`, or `worker/<slug>`; a segment is `[A-Za-z0-9][A-Za-z0-9_.-]*`. The main chat is never named `main`, which `SendMessage` reserves for the sender itself; a legacy `main` row still resolves, and its session start asks for the rename to `af-main`.
- The main chat is the row whose role is `main` and whose name has no `/`; `life/*` rows share the role but are side chats.
- `role` follows the prefix: `af-main`, a legacy `main`, and `life/*` are `main`, `project/*` is `operator`, `system/*` is `builder`, `worker/*` is `worker`.
- `model`: what main proposed, or `-`.
- `class`: see [Session classes](#session-classes).
- `status`: `live` (a hook touched the row within two hours), `idle` (older, not ended), or `ended <ts> <reason>` with reason `clear`, `resume`, `logout`, `exit`, or `other`.
- Timestamps are local ISO minutes.

Each name has a folder, `system/sessions/<name>/`, holding an optional `brief.md` ([`handoff.md`](handoff.md) has both shapes), the chat's `handoff.md`, and for `system/*` and `worker/*` an optional `report.md`.

## Session classes

A class says how much context a chat should carry. It is not stored in the registry: the name gives the default, and a `class: main|side|build` line in the chat's `brief.md` frontmatter overrides it (`af session register <name> --session <id> --class <c>` writes that line into the brief; it refuses when there is no brief, and on a value outside the three).

| Class | Default for | Window | Soft nudge | Hard nudge |
|---|---|---|---|---|
| `main` | `af-main` (and a legacy `main`) | 350k | none | none |
| `side` | `life/*`, `worker/*` | 300k | none | none |
| `build` | `project/*`, `system/*` | 1M | 400k | 600k |

A hook cannot set a window or start a compaction. The window is the operator's (`/autocompact`); Claude Code's auto-compact handles `main` and `side`. For `build`, `af hook post-tool-use` runs after every tool, reads the last main-chain assistant usage from the transcript (input, cache read and cache creation tokens), and adds one nudge to the chat: soft once at the soft threshold, hard at the hard threshold and again each 50k above it. Each firing is claimed by creating a marker file in `system/logs/context-nudge/<session id>/` (`soft`, and `hard-<tokens>` for the hard threshold plus each 50k), so parallel tool calls say it once; a jump over several buckets fires the highest. Falling below the hard threshold removes the hard markers, falling below the soft threshold (or `af hook post-compact`, after every compaction) removes all of them. `af hook pre-compact` prints the chat's standing summary instructions (its name, role, brief, handoff and plan paths, the current step, decisions, open questions, files touched) on every compaction, manual or automatic. A compaction after the last reply makes the size unknown (the usage line before it describes a context that is gone): no nudge fires until the next reply, and `af session context` says the size is unknown until then. `af session context [name]` prints a chat's class, measured context, window and thresholds, and the auto-compact window that applies to its model (`modelSettings.<model id>.autoCompactWindow` in the user-level Claude settings, which it only reads): a chat that auto-compacts below its hard threshold never reaches that nudge, and the output says so.

## The Claude panel

`system/tools/claude_panel.ps1` (version 2) manages chats in the Claude Code panel of the VS Code window whose title holds the vault folder name. It sends no key events and no mouse events, and uses no clipboard: it reads and acts through Windows UI Automation patterns (read, Invoke, ExpandCollapse, SelectionItem, ScrollItem) and through the AgentFrame bridge extension (`system/vscode-bridge/`, installed once; see its README), which opens, reveals and closes chat tabs and prefills a new chat's input, through a file inbox under `system/logs/panel-bridge/`. Actions: `list`, `send -Session <id> -TextFile <path>`, `new -TextFile <path> -Model <name> [-GroupId <id>]`, `model -Session <id> [-Model <name>]` (without `-Model` it lists the picker's options), `archive -Session <id>`, `close-untitled`, and `selftest`, which the operator runs by hand: it creates a Haiku 5.5 chat named `zz-selftest-<HHmm>`, sends a one-word prompt, renames it, compacts it, sets and reads its model, closes its tab, and prints one PASS or FAIL line per step and the session id. The driver reads text from a UTF-8 file, never an argument, and never logs it. `af session compact` (on a running chat), `rename`, `start`, `archive` and `panel` call it; `AF_PANEL_DRIVER` names another program, as the tests do.

- How a send works. The chat's tab is closed (that ends its process), then opened again with the text, which the page puts in the input; the driver reads the input back and only then invokes `Send message`. A text that starts with `/` is sent as it is: no leading space is added anywhere, and the slash palette does not open for a prefilled text. A chat with no open tab skips the close; a chat that was closed before is closed again afterwards when the text was a slash command (a plain prompt leaves its tab open, because the chat is running the turn). The chat keeps its own model across the close and reopen.
- One run at a time. Every action but `list` holds `system/logs/panel-bridge/driver.lock` (JSON: pid, the process's start time, session id, action, start) as an open file handle, so it is released when the process dies; a lock file left behind is taken over. `af` judges a lock by pid and start time together: a pid that is dead, or alive but started at another time (reused), does not hold it. A second run waits for it within its own budget, then exits 3. `list` takes it only when it must restore a minimized window. The closed-route `af session compact` holds the same lock (action `headless-compact`) for its whole `claude -p` run, so no driver run opens the chat in the second before its process writes a session record.
- The unbroken check. Tab labels are cut to 25 characters, and closing a tab throws away a draft in its input, so the driver closes a tab only right after one check that has no wait in it and is followed by nothing but the close: the window is not minimized; exactly one Claude tab carries the label (for `close-untitled`, the first of them) and it is the active tab; the target's row is the only active row and says idle; the chat's live records all say `status: idle`; the input is empty, which means Send is disabled and the input's value, read, is blank or one of the page's fixed placeholders (anything else is exit 4: with Send enabled it is a draft; with Send disabled the message says the input shows text of a given length the driver does not recognise, never the text, and that the placeholder list needs an update if he has no draft there); for the driver's own tab, the chat's one process is the one its open started, and the input holds exactly its text or is empty; the operator is still idle. Bridge 0.2.0 checks once more, right before it closes, that the tab is still the active one. Anything else and the check is retried after the next wait, and the run refuses (exit 5) when it never passes. It never closes a tab it did not open in this run unless the check passed for that chat, and when the tab it means to open was already there (the tab count did not grow by one) it stops (exit 5).
- Records. Only `status: idle` is idle: no status, or any other, is busy. Every `sessions/*.json` record whose pid is alive counts. A record whose entrypoint is not the VS Code panel means a terminal holds the chat, and the driver refuses (exit 5).
- Guards. The operator has been idle for 120 seconds (`-IdleSeconds`) before any step that changes his screen and again right before `Send message`; the input read-back equals the text exactly (a text with line breaks may read back with other breaks), and the Send it invokes is the one it verified: it re-reads only that input, that Send and the row, with no new search in between, otherwise nothing is sent (exit 5). A send is confirmed only when the input cleared and the transcript shows the user line, and for a slash command its effect (`/rename`: the new title; `/compact`: a new `compact_boundary` line); exit 0 only then.
- One deadline. `-WaitMinutes` (default 20) bounds the waits for the operator and the chat (then exit 3); the work after it gets 1200 seconds more, and the last 210 of them are kept for putting things back: 120 to wait for him, then 90 of their own for a closed chat's process to end and its tab to come back, so time spent waiting for him never cuts that short. Every step, the restore included, runs inside that. `list` reads only and has a deadline of its own: a 30-second wait and 45 seconds of work, and `af` stops it at 90 seconds. `af` kills the driver at its own limit, the wait plus 1200 seconds plus a 60-second margin (computed from the same numbers, which a test pairs), and a kill is logged to `system/logs/claude-panel.log`, reported as "af killed the panel driver; look at the chat now", and exits 1.
- What it changed. The driver tracks what it did to the chat (closed its tab, opened it, prefilled the text, pressed Send; a bridge step that got no answer in 25 seconds counts as attempted, and the tab list is read again to learn what happened, or the message says it is unknown) and every message, on every exit path, says it, then the tab's final state from a fresh read: open or closed from the bridge's tab list by the label rule (never from the chat's process, which outlives its tab for a while; a closed tab whose process still runs says so, and an unreadable list says unknown), and, when its tab is in front, what its input holds. After a failure before Send it puts the chat back: a tab it opened is closed again through the same unbroken check, as its own, and a tab that was open at the start is opened again whenever the tab list shows it closed, whatever happened to the cleanup, once the chat's process has ended (the panel opens no tab while it runs); when it does not end within the budget, a note says the reopen was not done and gives the `panel_bridge.py reveal` command that does it. After a confirmed send it closes only a tab it opened in this run for a chat whose tab was closed at the start, and only while its process is still the one its open started. Exit 3, 4 and 5 always mean nothing was sent. A send that was confirmed exits 0 even when a later cleanup fails; the cleanup failure is a note. The driver's notes (`note: ` lines on stderr) are printed by every `af` verb, on success and on refusal.
- The window. The driver never takes the foreground and never activates VS Code. A minimized VS Code window leaves its accessibility tree stale, so under the idle guard the driver saves the window's placement (`GetWindowPlacement`), moves the window to the bottom of the stack while it is still minimized, shows it without activation (`SW_SHOWNOACTIVATE`; measured: a window that was minimized from maximized comes back maximized, with no foreground change), places it directly behind his foreground window only when that window is not itself always-on-top (behind an always-on-top window VS Code would become always-on-top too, so it stays at the bottom), waits 2.5 seconds and reads the tree again. VS Code's extended style is read afterwards, the topmost bit is cleared if it is set, and a note says when it stays set. At the end the window is minimized again without activation (`SetWindowPlacement` with the saved flags and rectangle and showCmd `SW_SHOWMINNOACTIVATE`, never `SW_SHOWMINIMIZED`, which was measured to change the foreground, so a window that was maximized before it was minimized comes back maximized when he restores it). Minimizing a window he can see is a change he sees, so it is done only when this run restored the window, VS Code is not his foreground window, and either he is idle (at or above the threshold) or another window covers its centre point. With the no-focus restore VS Code can be the foreground window only because he brought it there himself, so then it is always left open and the run says `VS Code was left open: he has it in front`; in the other case where he can see it the run says `VS Code was left open: it is visible on his screen and he is at the computer`. The Window pattern's own restore is not used: it was measured to take the foreground and reset the system's last-input time, which made every later idle wait start over. The foreground window is read before and after the restore, and a change is a note, never a failure. If the check before a tab close finds the window minimized again (it can happen after the run's one restore), the close retry restores it again the same way. His previously active chat is put back (Invoke on its row) only when it is not active at the end, and only after he has been idle; a cancelled run does not wait for that.
- Why a run waits. While a run waits (the operator using the computer, a record saying busy, a running row, the lock held, a retry before a tab close, a full-screen window in front, the chat he has in front) it appends one line to `system/logs/claude-panel.log` per change of reason: time, action, session id, `waiting: <reason>`. A reason never holds a chat title or message text. The close retry reveals the chat on its first try and later only when its tab or row was not the active one, and waits 2 seconds between failed tries; before this a run could reveal a chat once a second for two minutes and say nothing.
- `archive -Session <id>` archives a chat in the panel's list. It is the one action that moves the pointer, because a row's `Archive session` button exists only while the pointer rests on the row (UI Automation focus does not show it); nothing is clicked or typed. Order: the lock, the guards (operator idle 120 seconds, the chat's records idle), the screen. The sessions list must be readable (the `New session` button is found), else exit 2. A list with no row for the chat exits 0 and says what is known: no row for this chat is in the list as shown (already archived, never listed, or inside a collapsed group); nothing was changed. A chat he has in front (its row is the active row) is never archived: the run waits within the wait budget for that to change and then exits 3, `it is the chat he has in front; nothing was changed`; what he has in front by then is what his view is put back to. A running row or a busy record is refused after the wait (exit 3). A chat with an open panel tab and an idle record has its tab closed first through the unbroken check (a draft is exit 4; a record from outside the panel is exit 5; the bridge is needed only in this case), and its row must stop being the active row within 5 seconds (else exit 3 and the tab is opened again, as after any failure before the archive). Then the row is scrolled into view, and one loop does all the waiting, before anything on his screen changes: he is idle; if another window covers the row's centre, no full-screen window is in front (`SHQueryUserNotificationState` 2, 3 or 4, which idle time alone cannot see; checked after the idle wait, so a video he started during it is seen; the driver waits within the run's wait budget, or 60 seconds of its own when that has already been spent, logs `a full-screen window is in front`, and exits 3 at the end with nothing raised or moved); and he is still idle at that moment. Then, with no wait in between, VS Code is raised above the covering window with `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)`, which takes no keyboard focus. Nothing waits after the raise except the 3-second button poll and the 5-second row-gone confirm, and anything not as required is exit 3 or 5 at once, so the raise is undone within about 8 seconds: if the row is still covered it is exit 5, if the idle time has dropped it is exit 3. The driver then reads and remembers the pointer, moves it to the row's centre (the position is taken from the target, so it is put back even if a read-back fails), and polls up to 3 seconds for a Button named `Archive session` among that row's own children. Right before the Invoke, with nothing waiting from there, it reads the chat again: no live session record at all, the row not running and not the active row, and he has not come back (the pointer is exactly where the driver put it and the idle time has not fallen below what it was before the move); otherwise exit 3, nothing archived. It invokes the button and confirms within 5 seconds that the row left the list (else exit 1). In every outcome after the pointer moved it puts the pointer back only if it is still where the driver put it, then undoes the raise to exactly where VS Code was: the first real window above VS Code and whether it is always-on-top are recorded just before the raise. Windows keeps a window's owned windows directly above it, so a bare `GW_HWNDPREV` is usually VS Code's own hidden window, which rises and drops with it; the walk therefore goes upward (at most 400 steps) and skips a window that is not visible, is cloaked (`DWMWA_CLOAKED`; a failed call counts as not cloaked), belongs to VS Code's process, or whose owner chain reaches the VS Code window. Undo clears topmost first, then, when the recorded window still exists and is not always-on-top, places VS Code directly behind it; when it was always-on-top, or none was found above, VS Code was the top real window and clearing topmost has put it back there; when it is gone, or the walk ran out of steps, VS Code goes behind his foreground window if that is not VS Code and not always-on-top, else to the back with a note. It is never placed behind an always-on-top window. The result is then checked against the screen instead of trusted: if the window that covered the row still exists and is visible, the row's centre must no longer belong to VS Code; if it does, VS Code is placed once more (behind that window, else behind his foreground window, else at the back) and, if it is still in front, a note says `VS Code is still in front of the window that covered the row`. A last read of VS Code's extended style clears the topmost bit once more if it is set, with a note if it stays. In the final clean-up each step (the pointer, the undo of the raise, his previous chat, minimizing again) is tried even when the one before threw, and a throw becomes a note that names the step. Messages are archive's own: nothing changed; the chat's tab was closed and is open again, or is not (with the reveal command); the Archive button was invoked and the row is still listed, gone, or could not be read. `af session archive` does not change the registry row; `af session end <name> --reason other` does that.
- Cancel. `-CancelFile <path>` makes a run that is only waiting and has changed nothing yet (the operator and chat guards, `Wait-Idle` before the first change, the wait for an idle row, the lock wait, archive's waits before its raise) stop through the normal exit path with exit 7, `cancelled; nothing was changed`. A cancelled run does not wait for him at the end to put his view back. When the run first changes the panel (a tab closed or opened, text prefilled) it writes the same path with the extension `.sending` and from then on never cancels. `af` passes the file only to the driver runs of a `--when-idle` waiter.
- Models. A model name matches an option only whole: the option equals it or starts with it and a space, so `Opus 5` never matches `Opus 5.5`. A new chat inherits the default model, which is the expensive one, so `new` and `af session start` require a model (`--model`; without one `af` refuses and lists the picker's options), and `new` sends nothing before the picker shows that model. A model pick in the panel writes the global `model` key in the user settings file as well as the chat's process, so every pick saves the key and the file's hash first, writes the key back right after the pick, and verifies both; if the file does not match the driver exits 6 with a message that says to fix `settings.json` by hand before anything else runs. `model` works on an idle chat by reveal, pick, restore.
- `close-untitled` closes the `Claude Code` tabs of chats that have had no message: each needs a live panel process whose record says idle and is at least 60 seconds old, no transcript and no row, and the close goes through the unbroken check under the lock; a draft stops it. `new` refuses while an untitled tab is open, and identifies its chat by the one new panel record its own open created.
- Exit codes: 0 done and confirmed; 1 failed or unconfirmed (after Send was pressed, the message says the text may have reached the chat); 2 bridge, window, chat or control not found (a bridge that does not answer `ping` in 10 seconds says how to install it; a chat running in a terminal has no panel row; for `archive`, a sessions list that is not readable); 3 operator active, chat busy or running, the chat he has in front or a full-screen window in front of its row (`archive`), or the lock held for the whole wait; 4 a draft in the chat's input; 5 a safety check failed; 6 the model key or settings file does not match after a pick; 7 cancelled through `-CancelFile` before anything was changed. `af` turns 2 to 7 into refusals. On 3, 4 and 5 nothing was sent (nothing was archived, for `archive`), and the message states the tab's final state.
- Every run appends one line to `system/logs/claude-panel.log`: time, action, session id, exit code, seconds (and its `waiting:` lines, above). Message text, `/rename` titles and chat titles are never logged.
- The verbs mostly wait, so an orchestrator hands the panel actions to a Sonnet subagent and keeps its own context. Never run them against the orchestrator's own chat.

## Start a worker

Register it, then start it with Bash `run_in_background`, so its exit wakes the chat that started it:

```
af session register worker/<x> --session <new-uuid> --model <m> --brief <path>
claude -p "<goal>" --session-id <uuid> --agent <role> --name worker/<x> --model <m> --permission-mode acceptEdits --strict-mcp-config --allowedTools "<the commands it runs>"
```

Use `claude -p`, not `claude --bg`, which refuses a workspace whose trust prompt was never accepted in a terminal. Put the prompt first: `--allowedTools` and `--tools` take every word after them. `--strict-mcp-config` leaves it no connector; drop it only for a brief that names one. The exit notification is the worker's return; a `SendMessage` from a worker in another permission mode is held.

## Reach a chat

`af session reach <name>` prints one of these and what to do next. A roster status of `shell` counts as `busy`; a chat the roster does not list is `closed`, and any other status this build does not know is `unknown`, never `closed`. `af session list` shows `unknown` (never `absent`) for a roster entry with no status. `SendMessage` answers `success: true` in every case but `closed`, so its result never proves a turn started; `af session reach <name> --confirm "<phrase>" --since <time>` does, with the `--since` value the first reading printed before you sent.

| State | Meaning | What to do |
|---|---|---|
| `live-idle` | Running, nothing in progress, same permission class | Send; a new turn starts there |
| `live-busy` | Running a turn, same permission class | Send; it lands between tool calls in that turn |
| `live-waiting` | Stopped at a permission prompt or question | Tell him; a message waits behind his answer |
| `holding` | The sender and the target differ in bypass versus prompting, or the setting is `hold` | Do not send; in a VS Code chat it expires unread in about five minutes. Tell him: the modes must match or `crossSessionInbound` must be `accept` in his `/config` |
| `refusing` | `crossSessionInbound` is `refuse` | Tell him; the message is dropped |
| `closed` | Not listed on this machine's roster | `SendMessage` refuses. Start a turn with Bash `run_in_background`: the command `af session reach` prints, which denies the connector's order and flow tools by name and takes `--allowedTools` for what the job runs, since a headless turn is denied anything else. Never resume a chat that is running |
| `unknown` | No `claude agents` roster, or the roster lists the chat with no status or one this build does not know (it is running, but idle or busy is not known) | Say the state is unknown |

A live chat's held or expired message also reaches the sender as a system notice within seconds, naming the recipient. A side chat that needs main runs the same check with `--from <its name>`; when it says `holding` or `closed`, the point goes in its handoff and in its reply to him. `notify_when_idle` wakes the asker only for a target in its own permission class, or one it spawned; otherwise the notice is only logged.

| Verb | Effect |
|---|---|
| `af session register <name> --session <id> [--model <m>] [--brief <path>] [--class <c>]` | Writes the row, creates the folder, copies the brief, and with `--class` writes its `class:` line |
| `af session list [--json]` | Prints the rows with their effective status and class |
| `af session context [name]` | Prints a chat's class, context tokens, window, thresholds and auto-compact window; with no name, a table of every live chat that has a transcript |
| `af session stop`, `af hook stop` | Stamp `last_seen`; ask for a handoff when it is missing, has no `written:` line, or is stale, and say which and how to fix it (never for `main`) |
| `af session end`, `af hook session-end` | Set `ended` |
| `af session compact <name> [--model <m>] [--instructions "<text>"] [--force] [--dry-run] [--when-idle] [--wait-minutes <n>] [--then-file <path>]` | Compacts a chat. A chat with no live process is compacted from outside: `claude -p "/compact <text>" --resume <id>` from the vault root, then checks the transcript gained a `compact_boundary` line and prints the context before, the model and where it came from, and the cost. That route fails closed: it runs only when the session id is absent from the `claude agents --json --all` roster (an entry in any status counts as running, and so does an entry with no status or an unknown one) and no `sessions/*.json` record in the Claude config dir names it; no roster refuses it (close its tab and rerun, or run it through the panel). It checks again after the run and exits 1 with a warning if the chat went live meanwhile. A running chat is compacted through [the panel](#the-claude-panel): the driver sends `/compact <text>`, and the verb waits up to 10 minutes for a new `compact_boundary` line, failing honestly without one. `--when-idle` returns at once after starting a detached waiter that runs this once the chat and the operator are idle, within `--wait-minutes` (default 60; 20 without `--when-idle`); its outcome is appended to `system/logs/panel-waiters.log`, and this is how a chat compacts itself. A chat has at most one pending waiter (its job file is `system/logs/claude-panel/waiter-<session id>.json`, created only when absent; a left-over job is replaced by a compare-and-rename, never deleted first): a second `--when-idle` names the live one and exits 0. A job is left over once its waiter's pid is dead or started at another time, or once its queue time plus its wait plus the most a waiter may run after its wait (two driver runs, the boundary wait and two minutes) has passed; the waiter cuts each driver run's wait, the boundary wait and the headless run to end by that same time, so a job is never expired while its waiter can still run. The waiter picks its route when it fires, waits while any live record is not idle, and does nothing when the transcript gained a `compact_boundary` after it was queued. A failed waiter writes one line to `system/logs/context-nudge/<session id>/waiter-result.txt` of the chat that queued it (`CLAUDE_CODE_SESSION_ID` when the verb ran in a chat), worded for who queued what; with no caller known it goes to the compacted chat and says so. That chat is shown it once, at its next tool call or stop; a success is silent. The closed route is also refused while a live panel driver holds the lock for that chat. It takes the panel lock for its whole run, waiting for it up to 10 minutes (a waiter: what is left of its wait), then refuses, naming the holder's action and session. `--then-file` sends that file's text to the chat as its next message after the compaction is confirmed, under the same guards. `af session compact --cancel <name>` stops a queued `--when-idle` compaction: it writes `system/logs/claude-panel/waiter-<session id>.cancel` next to the job file, which the waiter looks for while it waits for the chat (its poll), while it waits for the panel lock, and, as `-CancelFile`, in every wait of its driver run that has changed nothing yet; it then waits up to 20 seconds for the job file to go and says exactly one of: cancelled (the waiter removed the marker, its text copy and then the job file, logged `cancelled` to `panel-waiters.log`, ran no `--then-file` step and left no failure line for the chat); no job queued for the chat (a job file of a dead waiter does not count); already being sent and not cancelled (the driver, or the closed route, had begun changing things and wrote the `.sending` marker; the cancel takes its marker back); the waiter had already ended before it looked; or the processes were still running after 20 seconds (the marker is written; the waiter's pid and the driver's are named and nothing is killed; if the driver has already begun changing the panel it will finish the compaction, otherwise it stops at its next check, so run the command again to see). A stale marker is removed when a new job is queued. `--when-idle` prints the cancel command. `--cancel` cannot be combined with the compaction's other options. Also refuses a transcript under 50k tokens without `--force`, and on the closed route a haiku model. A chat whose transcript already ends at a `compact_boundary` with no reply since is `already compact`: it prints that and that `--force` runs it anyway, exits 0, and runs nothing, `--dry-run` included; with `--force` it compacts (a reply that failed with zero usage after the boundary looks the same), taking the model from the reply before the boundary. The closed-route summary model is `--model`, else the last reply's `requestedModel` (the `[1m]` form), else its `message.model`; the standing summary instructions come from `af hook pre-compact`, and `--instructions` adds to them |
| `af session archive [<name>] [--session-id <id>] [--wait-minutes <n>] [--dry-run]` | Archives a chat in the panel's list through the driver's `archive` action ([the panel](#the-claude-panel)): it closes the chat's open tab first when it has one and no draft, rests the pointer on the chat's row, invokes the row's `Archive session` button, confirms the row left the list and puts the pointer back. `<name>` resolves through the registry to the session id; `--session-id` (8 to 64 hex digits and dashes) is for a chat with no registry row, and then `<name>` is omitted (with both, the id must be the row's). It refuses the calling chat itself (the session id in `CLAUDE_CODE_SESSION_ID`). The registry row is not changed: the output names `af session end <name> --reason other` as the way to close it. A list with no row for the chat exits 0 and the driver's words are printed unchanged (no row for this chat is in the list as shown; nothing was changed). A chat he has in front is refused (exit 3) after the wait. Driver exit 3, 4 and 5 become refusals that say nothing was archived; 7 says it was cancelled. `--dry-run` prints the driver call and runs nothing |
| `af session rename <name> [--to <text>] [--wait-minutes <n>]` | Sends `/rename <text>` through the panel (the text defaults to the registry name), then reads the panel row back and fails when it does not show the new name |
| `af session start <name> --brief-prompt-file <path> --model <m> [--group <name>] [--wait-minutes <n>]` | Opens a new chat in the panel with the file as its first message, sets and confirms `--model` first (required; without it the verb refuses and lists the options; the pick is saved and restored around the global model key), and prints the new session id; the chat's own first act is `af session register`. `--group <name>` puts the chat in an existing session group: the name is resolved to the group id by reading the extension's stored groups read only (a copy of VS Code's `state.vscdb`, table `ItemTable`, key `Anthropic.claude-code`, inner key `sessionGroups:<vault root>`); an unknown name is refused with the list of group names, and nothing creates a group |
| `af session panel [--json]` | The chats the panel lists (session id, panel name, idle or running, active), joined with registry names |
| `af session reach <name> [--from <name>] [--confirm "<phrase>" --since <time>] [--json]` | Prints what a message would meet, what to do next, and the `--since` value; `--confirm` exits 0 once the target's Claude read an inbound message holding that phrase at or after that time, 3 until then, and refuses a phrase under 12 characters |
